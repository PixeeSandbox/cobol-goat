🎓 Security Notes

The account lookup endpoint accepts an account ID from the user with no authorization check. There is no verification that the logged-in user is actually allowed to view the requested account.

ACCTVIEW.cbl 
       WORKING-STORAGE SECTION.
       01  WS-REQUEST-ACCT-ID   PIC 9(8).   *> From user input
       01  WS-SESSION-USER-ID   PIC 9(8).   *> From session

       PROCEDURE DIVISION.
       VIEW-ACCOUNT.
           *> No ownership check — any authenticated user
           *> can retrieve any account by ID
           EXEC SQL
               SELECT acct_number, owner, ssn, balance, role
               INTO :WS-ACCT-NUMBER, :WS-ACCT-OWNER,
                    :WS-ACCT-SSN, :WS-ACCT-BALANCE, :WS-ACCT-ROLE
               FROM accounts
               WHERE acct_id = :WS-REQUEST-ACCT-ID
               *> Missing: AND owner_id = :WS-SESSION-USER-ID
           END-EXEC.

Without the ownership check, the WHERE clause only filters by account number — which you control. Just enumerate account IDs starting from 1001. Account 1003 belongs to the admin.

Impact

Any authenticated user can view any account — name, SSN, balance, role. This is a complete confidentiality failure exposing PII and financial data.

Fix

Fixed version — add ownership check
           EXEC SQL
               SELECT acct_number, owner, ssn, balance, role
               INTO :WS-ACCT-NUMBER, :WS-ACCT-OWNER,
                    :WS-ACCT-SSN, :WS-ACCT-BALANCE, :WS-ACCT-ROLE
               FROM accounts
               WHERE acct_id = :WS-REQUEST-ACCT-ID
               AND owner_id = :WS-SESSION-USER-ID
           END-EXEC
  • Always enforce ownership in the DB query, not just in application logic
  • Use indirect references (session-scoped tokens) instead of raw sequential IDs
  • Log and alert on access to accounts not owned by the requesting session
