🎓 Security Notes

The COBOL admin check reads the user's role from the HTTP request body — not from the server-side session. Any user can claim to be admin by simply sending role=admin in their request.

ADMINCHK.cbl 
       WORKING-STORAGE SECTION.
       01  WS-REQUEST-USER-ID   PIC 9(5).
       01  WS-REQUEST-ROLE      PIC X(20).  *> From request body!
       01  WS-REQUEST-ACTION    PIC X(50).

       PROCEDURE DIVISION.
       CHECK-ADMIN-ACCESS.
           *> Role read from user-supplied input
           *> instead of from the server-side session
           MOVE 'DENY' TO WS-ADMIN-RESULT
           IF  WS-REQUEST-ROLE = 'admin'
               MOVE 'ALLOW' TO WS-ADMIN-RESULT
               PERFORM EXECUTE-ADMIN-ACTION
           ELSE
               DISPLAY 'Access denied'
           END-IF.

Change the Role dropdown from user to admin and click Execute. The server trusts the role you send in the request body instead of looking it up from your session.

Impact

Any authenticated user can perform arbitrary admin actions — deleting users, resetting the database, viewing all PII — simply by setting role=admin in their request.

Fix

Fixed version — look up role from session store
       *> Look up role from session, not from request
       EXEC SQL
           SELECT role INTO :WS-SESSION-ROLE
           FROM sessions
           WHERE session_id = :WS-SESSION-TOKEN
       END-EXEC
       IF WS-SESSION-ROLE = 'admin'
           PERFORM EXECUTE-ADMIN-ACTION
       END-IF
  • Never trust role or privilege data supplied by the client
  • All authorization decisions must reference server-side session or token state
  • Apply defence-in-depth: DB queries should also check the server-validated role
